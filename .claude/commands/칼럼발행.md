# /칼럼발행

`/칼럼쓰기`·`/칼럼업데이트`·`/칼럼삭제`로 이미 만들어진 칼럼 관련 변경사항을 commit/push합니다.
**이 명령은 콘텐츠를 만들거나 다시 쓰지 않습니다** — 검증된 변경사항을 안전하게 반영하고, 이미
만들어진 FAQ의 발행 상태를 칼럼과 맞추는 역할만 담당합니다. 이 명령만이 칼럼/FAQ 관련 git
commit/push를 수행합니다. 새 FAQ를 만들거나 FAQ 본문을 고치는 것은 `/칼럼쓰기`·`/학술칼럼쓰기`의
역할입니다(`docs/06-CONTENT-WORKFLOW.md` §16) — 이 명령은 이미 그 단계에서 만들어진 FAQ의
`draft` 플래그만 다룹니다.

사용자 입력(`$ARGUMENTS`): 발행할 칼럼의 slug, 또는 명시가 없으면 직전 작업 결과를 사용합니다.

## 1. 발행 전 확인 (하나라도 문제가 있으면 여기서 멈추고 사용자에게 보고)

1. `git status`로 현재 워킹트리 상태를 확인하세요.
2. `git diff`로 실제 변경 내용을 확인하세요.
3. 이번 변경이 신규 발행(Add)/수정(Update)/삭제(Delete) 중 무엇인지 `git status`로 판단하세요.
4. **신규 발행 또는 수정인 경우**: 대상 칼럼의 MDX 파일(`content/columns/<slug>.mdx`)이 실제로 존재하는지, frontmatter의 `thumbnail`이 가리키는 이미지 파일이 실제로 `public/`에 존재하는지 확인하세요.
5. **신규 발행인 경우**: frontmatter의 `draft`가 `true`인지 확인하고, 발행을 위해 `false`로 변경하세요(이미 `false`라면 왜 그런지 확인 — 이미 발행된 글일 수 있습니다). **수정/삭제 작업에서는 `draft` 값을 임의로 바꾸지 마세요.**
6. **삭제인 경우**: `/칼럼삭제`가 이미 파일을 지워 사용자 승인까지 받은 상태인지 확인하세요. 이 명령에서 새로 삭제를 결정하지 않습니다.

## 1-B. FAQ Knowledge Base 발행 동기화 (신규 발행 또는 수정으로 draft 칼럼이 publish되는 경우에만)

이 칼럼이 새로 `draft: false`로 전환되는 경우에만 해당합니다. 수정(이미 발행된 글의 내용만 바뀌는 경우)이나 삭제에는 해당하지 않습니다.

1. `content/faq/*.mdx` 전체에서 `draft: true`이면서 `relatedColumnSlugs`에 이번 칼럼의 slug를 포함한 FAQ를 찾으세요.
2. **없으면** 이 단계를 건너뛰고 바로 §1-C(검증 재실행)로 넘어가세요 — FAQ 없이 칼럼만 발행하는 것은 정상입니다.
3. **있으면** 찾은 FAQ 전체를 사용자에게 보여주고, 각각 지금 함께 발행할지 물어보세요:
   - 질문(`question`)
   - `category`
   - `slug`
   - 이 칼럼과의 관계(예: "이 칼럼의 핵심 결론을 짧게 답하는 FAQ")
   - 첫 문단(=JSON-LD로 노출될 답변)
4. **반드시 개별 선택으로 물어보세요.** "전부 함께 발행"을 기본값으로 강제하지 마세요. FAQ가 여러 개면 A는 발행, B는 발행, C는 draft 유지처럼 각각 다르게 선택될 수 있습니다.
5. 사용자가 발행을 선택한 FAQ만, 해당 파일의 `draft: true`를 `draft: false`로 바꾸세요. **question/category/aliases/relatedTreatmentSlugs/relatedColumnSlugs/본문 등 다른 어떤 필드도 건드리지 마세요.** 새 FAQ를 만들거나 기존 FAQ 본문을 다시 쓰지 마세요 — 그건 `/칼럼쓰기`·`/학술칼럼쓰기`의 범위입니다.
6. **사용자가 특정 FAQ의 발행을 원하지 않아도 칼럼 발행 자체는 막지 마세요.** 발행하지 않은 FAQ는 `draft: true`로 그대로 둡니다 — 이미 이 칼럼의 `relatedColumnSlugs`에 연결되어 있으므로, 나중에 그 FAQ가 따로 발행되면 자동으로 링크가 보입니다.
7. 이미 `draft: false`(published)인 FAQ가 이 칼럼을 `relatedColumnSlugs`로 참조하고 있다면 **아무것도 하지 마세요.** 그 FAQ를 다시 발행할 필요는 없습니다 — 칼럼이 publish되는 순간 `app/faq/[category]/page.tsx`의 기존 필터(Step 1)가 자동으로 링크를 노출합니다. FAQ 파일을 열어 확인만 하고 편집하지 않습니다.

## 1-C. 검증 재실행

1. 아래 검증을 **다시** 실행하세요(직전 작업 이후 다른 변경이 있었을 수 있습니다 — FAQ의 `draft` 값을 바꿨다면 특히):
   ```bash
   npm run validate:content
   npm run validate:seo
   npm run typecheck
   npm run lint
   npm run build
   ```
2. `git status`/`git diff`에 이번 칼럼(과 방금 발행 동기화한 FAQ)과 무관한 다른 작업의 변경 파일이 섞여 있는지 확인하세요. 섞여 있다면 그 사실을 사용자에게 먼저 보고하고, 무관한 파일은 커밋에 포함하지 마세요.

## 2. 모든 검증이 통과한 경우에만 진행

- `git add`는 이 칼럼과 **직접 관련된 파일만** 명시적으로 지정하세요(예: `git add content/columns/<slug>.mdx public/images/columns/<slug>.webp`). 1-B에서 함께 발행하기로 한 FAQ가 있다면 그 파일도 명시적으로 추가하세요(예: `git add content/faq/<faq-slug>.mdx`). **`git add .`나 `git add -A`는 사용하지 마세요.**
- 커밋 메시지는 `docs/06-CONTENT-WORKFLOW.md` §9의 컨벤션을 기본으로 하되, 함께 발행한 FAQ가 있으면 이어서 명시하세요:
  - 신규 발행: `Add column: <slug>`
  - 수정 반영: `Update column: <slug>`
  - 삭제 반영: `Delete column: <slug>`
  - 함께 발행한 FAQ가 있을 때: `Add column: <slug> (+ publish FAQ: <faq-slug-1>, <faq-slug-2>)`
- `git commit`
- `git push origin main`

## 3. 절대 하지 말 것

- `git add .` / `git add -A`
- 이번 칼럼과 무관한 파일을 커밋에 포함
- 검증이 하나라도 실패한 상태에서 commit/push
- `git push --force` / `git push -f`
- `git reset --hard`
- `git rebase`
- `main` 이외의 브랜치로 push하거나 새 브랜치 생성(별도 지시가 없는 한)
- 콘텐츠 본문·frontmatter를 이 명령에서 직접 수정 — 그건 `/칼럼쓰기`·`/칼럼업데이트`의 역할입니다.
- **새 FAQ를 만들거나 기존 FAQ의 question/본문/근거/aliases/관련 링크를 수정** — 이 명령이 FAQ 파일에서 바꿀 수 있는 값은 사용자가 발행에 동의한 FAQ의 `draft` 필드 하나뿐입니다.
- 사용자에게 개별로 묻지 않고 연결된 FAQ를 전부 자동으로 함께 발행
- FAQ 발행 여부를 이유로 칼럼 발행 자체를 보류

이 중 하나라도 필요해 보이는 상황이면, 실행하지 말고 사용자에게 먼저 물어보세요.

## 4. 최종 보고

- 커밋 해시
- 커밋 메시지
- push한 브랜치
- 운영 URL(`https://ysbsdc.com/column/<slug>` — 실제 DNS가 아직 Vercel로 전환되지 않았을 수 있으므로, 현재 어느 상태인지도 함께 안내)
- **FAQ Knowledge Base 발행 동기화 결과**:
  - 함께 발행한 FAQ (질문 / slug / 이전에는 어느 관계였는지)
  - draft로 남긴 FAQ (있다면, 왜 유지했는지)
  - 이미 published라서 손대지 않은 FAQ (있다면)
  - 연결된 FAQ 자체가 없었다면 "해당 없음"
- Vercel 배포 상태는 코드에서 확인할 수 없으므로, 사용자가 Vercel 대시보드에서 직접 확인해야 한다는 점을 명시하세요.

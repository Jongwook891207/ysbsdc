# /칼럼쓰기

주어진 주제 또는 완성 원고를 바탕으로 `content/columns/`에 새 칼럼 MDX 파일을 생성합니다.
이 명령은 **파일 생성과 검증까지만** 수행합니다. `git add`/`commit`/`push`는 어떤 경우에도 하지 않습니다.

사용자 입력(`$ARGUMENTS`): 주제 또는 완성 원고, 그리고 선택적으로 제목/핵심 메시지/category/tags/FAQ.
첨부 이미지가 있다면 아래 "썸네일 처리" 절차를 따릅니다.

## 0. 시작 전 — 문서·구조 확인 (매번 다시 확인, 캐시된 지식 신뢰 금지)

**0-A. 콘텐츠 철학 문서 (가장 먼저, 매 실행마다 실제 파일을 다시 Read)**

문서 내용을 이 명령 파일에 옮겨 적지 않고, 실행할 때마다 아래 파일을 직접 다시 읽습니다 —
그래야 문서가 수정되면 다음 실행부터 자동으로 반영됩니다.

1. `docs/00-AI-WRITING-CONSTITUTION.md`
2. `docs/01-BRAND-BIBLE.md`
3. `docs/02-INTERVIEW.md`
4. `docs/03-WRITING-GUIDE.md`
5. `docs/04-MEDICAL-COMPLIANCE.md`
6. `docs/05-SEO-AEO.md`
7. `docs/06-CONTENT-WORKFLOW.md`

문서가 비어 있거나 초안 상태라면, 있는 것처럼 요약하거나 추측으로 채우지 말고 그 사실을 그대로
보고한 뒤 진행하세요.

이 문서들은 일렬 우선순위가 아니라 각자 역할이 다릅니다 — `CLAUDE.md`의 "문서 역할"을 따르세요.
실제 규칙이 충돌하면 **00 → 04 → 01 → 03 → 05** 순서로 판단합니다. **02(인터뷰)는 이 순서에
포함되지 않습니다** — 우선순위 규칙 문서가 아니라 원장의 실제 사고방식·사실을 확인하는 근거
자료이므로, 02의 내용이 불명확하거나 다른 문서와 충돌하는 것처럼 보이면 임의로 결론 내리지 말고
사용자에게 확인하세요. **06(워크플로우)도 이 순서에 포함되지 않습니다** — 이 명령 자체의 실행
절차가 곧 06이 정의한 절차입니다.

**0-B. 실제 코드 구조**

프로젝트가 이 사이 바뀌었을 수 있으므로, 아래도 **이번 실행에서 직접 다시 읽고** 시작하세요.

- `lib/content/schemas.ts` — 현재 실제 frontmatter 스키마(zod). 아래 "frontmatter 필드" 절은 작성 시점 기준 요약이며, 실제 스키마와 다르면 **스키마가 우선**입니다.
- `content/columns/*.mdx` 기존 파일 2~3개 — 실제 문체와 포맷 확인
- `lib/treatmentAnchors.ts` — 실제 존재하는 진료 앵커 목록
- `content/authors/*.mdx` — 실제 존재하는 작성자 slug 목록
- `components/content/mdx/mdxComponents.tsx` — 실제로 구현된 MDX 컴포넌트 목록

## 1. frontmatter 필드 (작성 시점 기준 — 위 0-B에서 재확인 필수)

`lib/content/schemas.ts`의 `contentFrontmatterSchema` 기준. **이 목록에 없는 필드를 추측으로 추가하지 마세요** — 스키마가 `.strict()`라 알 수 없는 필드는 build 시점에 에러가 됩니다.

- `title` (필수, 문자열 — 제목 형식에 대해서는 "본문 작성 규칙" 절 참고)
- `slug` (필수, `^[a-z0-9]+(-[a-z0-9]+)*$` — 영문 소문자·숫자·하이픈만)
- `summary` (필수, 카드/목록에 노출되는 짧은 요약)
- `description` (필수,메타 description·OG용, summary와 다른 문구 권장)
- `publishedAt` (필수, `YYYY-MM-DD`, 오늘 날짜 사용)
- `updatedAt` (선택, `YYYY-MM-DD`, 신규 글이면 생략)
- `authorSlug` (필수, `content/authors/`에 실제 존재하는 slug만 — 0-B에서 확인한 목록 사용, 추측 금지)
- `reviewedBySlug` (선택, 실제로 작성자와 다른 검토자가 있을 때만. 없으면 생략 — 억지로 authorSlug와 같은 값을 넣지 않음)
- `lastReviewed` (선택, `reviewedBySlug`가 있을 때만 함께 필수 — 스키마가 이 조합을 강제함)
- `category` (필수, 자유 문자열 — 기존 카테고리와 자연스럽게 겹치는지 0-B에서 확인한 기존 글들과 비교)
- `tags` (배열, 중복 금지 — 스키마가 중복을 에러로 처리함. 과도하게 늘리지 말 것)
- `thumbnail` (필수, `/`로 시작하는 루트 상대 경로 또는 `https://` — 아래 "썸네일 처리" 절차로 결정)
- `relatedTreatmentSlugs` (선택, `lib/treatmentAnchors.ts`에 실제 존재하는 키만 — 이 글의 주제와 진짜 관련 있을 때만 넣고, 없으면 생략)
- `featured` (boolean, 지시받지 않았으면 `false` — 임의로 `true`로 올리지 않음)
- `draft` (boolean — 이 명령은 발행 명령이 아니므로 **항상 `true`로 생성**. `/칼럼발행`에서 `false`로 전환)
- `faq` (선택, `[{question, answer}]` 배열 — 실제로 원고에 담긴 Q&A가 있을 때만. 화면에 없는 질문을 지어내지 않음)

## 2. 본문 작성 규칙

- H1을 절대 넣지 마세요. 페이지 템플릿이 `frontmatter.title`을 H1으로 렌더링합니다. 본문 첫 heading은 `##`(H2)부터.
- 일반 마크다운(문단/리스트/굵게/링크)을 우선 사용하세요.
- 특수 MDX 컴포넌트는 0-B에서 확인한 `mdxComponents.tsx` 목록에 실제로 있는 것만, 꼭 필요할 때만 최소 사용:
  - `<Callout title="...">` — 일반 안내 박스
  - `<Warning title="...">` — 주의/유의 사항(테라코타 톤, 경고색 아님)
  - `<Quote cite="..." role="...">` — 문헌/원장 인용. **환자 후기 아님**
  - `<DoctorComment doctorSlug="kim-jongwook">` — 원장 코멘트 박스. `doctorSlug`는 실제 author slug만
  - `<Checklist items={["...", "..."]}>` — 점검 목록
  - `<CTA variant="gold">예약 문구</CTA>` — 기본 href는 실제 예약 URL(`CLINIC.bookingUrl`)
  - **`Testimonial`, `FAQBox`는 존재하지 않습니다.** 절대 사용하지 마세요(빌드 에러가 됩니다). 환자 후기 콘텐츠는 이 프로젝트에 아직 없습니다.
- 제목 형식: `docs/05-SEO-AEO.md`의 질문형 제목 권장은 **권장사항이지 강제가 아닙니다.** 검색
  의도와 자연스러움에 맞으면 이유형·설명형 제목도 허용됩니다. 기존에 발행된 글의 제목을 이 기준으로
  소급 수정하지 마세요.
- 관련 진료 링크(`relatedTreatmentSlugs`)와 본문 내 다른 페이지 링크는 실제 존재하는 경로만 사용하세요(`/treatment#implant` 등 0-B에서 확인한 값, `/column/[다른 실제 slug]` 등). 존재하지 않는 경로를 만들지 마세요.
- 의료적 사실·통계·경력·환자 사례를 임의로 만들어내지 마세요. 사용자가 준 원고/입력에 없는 내용은 추가하지 않습니다.
- 환자 개인정보(이름, 생년월일, 연락처, 얼굴이 드러나는 사진 등)를 절대 포함하지 마세요.
- **의료광고 금지 표현 검사는 `docs/04-MEDICAL-COMPLIANCE.md`의 최신 내용을 직접 읽고 그 기준 그대로 적용하세요.** 0-A에서 이미 다시 읽었을 04를 기준으로 삼고, 별도로 요약된 금지어 목록을 이 명령 파일 안에 두지 않습니다 — 04가 수정되면 다음 실행에 자동 반영되어야 합니다. `docs/00`/`docs/01`의 금지 표현 예시는 브랜드 철학 차원의 참고일 뿐, 세부 판정 기준은 항상 04입니다.
- 기존 글(0-B에서 읽은 파일)의 문체를 유지하세요. 임의로 어조를 바꾸지 않습니다.

## 3. slug 생성

- 사용자가 slug를 명시하지 않았으면 제목/주제에서 의미를 살린 영문 kebab-case slug를 생성하세요(예: `why-we-recommend-second-opinions`).
- 생성 전 `content/columns/`에 동일 slug 파일이 이미 있는지 확인하고, 있으면 다른 slug를 제안하세요.
- 파일명은 반드시 `slug.mdx`와 정확히 일치해야 합니다(로더가 파일명과 frontmatter.slug 불일치를 에러로 처리합니다).

## 4. 썸네일 처리

**첨부 이미지가 로컬 파일로 접근 가능한 경우:**
1. 실제 파일 경로를 확인하세요(존재하지 않으면 다음 절 "찾을 수 없는 경우"로).
2. 아래 명령으로 리사이즈·크롭·WebP 변환을 시도합니다(새 패키지를 설치하지 않습니다 — `sharp`는 `next`의 기존 의존성으로 이미 `node_modules`에 있습니다):
   ```bash
   node scripts/process-column-thumbnail.mjs "<원본 경로>" "<slug>"
   ```
3. 이 스크립트는 성공 시 마지막 줄에 최종 상대 경로(예: `/images/columns/<slug>.webp`)를 출력합니다. 이 값을 그대로 `thumbnail`에 사용하세요.
4. 만약 스크립트가 "sharp is not available" 메시지와 함께 원본 확장자 그대로 저장했다면, 정직하게 "WebP 변환 실패, 원본 형식 유지"라고 보고하세요 — 변환에 성공했다고 거짓 보고하지 마세요. 이때도 `sharp`나 다른 이미지 도구를 임의로 새로 설치하지 마세요.
5. 결과 이미지가 실제로 `public/images/columns/`에 존재하는지 `ls`로 다시 확인한 뒤에만 frontmatter에 반영하세요.

**첨부 이미지를 찾을 수 없는 경우:**
- 저장했다고 거짓 보고하지 마세요.
- 사용자에게 로컬 파일 경로를 알려주시거나 프로젝트 폴더에 넣어달라고 요청하세요.

**썸네일이 전혀 없는 경우:**
- `thumbnail`은 스키마상 필수 필드라 비워둘 수 없습니다. 존재하지 않는 경로를 임의로 지어내지 마세요.
- 0-B에서 확인한 `public/images/` 기존 이미지 중 주제상 의미가 통하는 것을 재사용할지, 사용자에게 이미지 제공을 요청할지 정책을 먼저 보고하고 사용자 지시를 기다리세요.

## 5. 검증 (반드시 직접 실행)

```bash
npm run validate:content
npm run validate:seo
npm run typecheck
npm run lint
npm run build
```

하나라도 실패하면 원인을 고치고 재실행하세요. 실패 상태로 "완료"라고 보고하지 마세요.

## 6. 절대 하지 말 것

- `git add`/`commit`/`push` — 이 명령의 범위가 아닙니다.
- `draft: false`로 생성 — 발행은 `/칼럼발행`의 역할입니다.
- **schema 변경** (`lib/content/schemas.ts` 등) — frontmatter가 부족해 보여도 스키마를 넓히지 말고, 그 사실을 사용자에게 보고하세요.
- **디자인/CSS 리팩토링** — 이 명령의 목적이 아닙니다.
- **기존 코드 정리(리팩토링)** — 요청받지 않은 범위입니다.
- **칼럼과 무관한 파일 수정.**
- **새 패키지 임의 설치** — 이미지 변환 도구가 없어도 `npm install`을 실행하지 않습니다(4번 참고).

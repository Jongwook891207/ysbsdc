# /학술칼럼쓰기

논문·임상 가이드라인을 근거로 삼는 학술형 원장 칼럼을 작성합니다. 일반 진료 철학 글이나 가벼운
환자 설명 글은 이 명령이 아니라 `/칼럼쓰기`를 사용하세요 — 이 명령은 `docs/07`의 엄격한 문헌
검증 절차를 전제로 하므로, 학술 근거가 핵심인 글에만 씁니다.

사용자 입력(`$ARGUMENTS`): 다루고 싶은 임상 주제, 그리고 있다면 이미 확보한 논문/가이드라인
자료(PDF, DOI, 서지정보 등).

**이 명령은 반드시 2단계로 나뉩니다. 1단계가 끝나면 멈추고 사용자의 승인을 기다리세요. 문헌과
구성안이 승인되기 전에는 `content/columns/`에 파일을 만들지 않습니다.**

## 0. 시작 전 — 매 실행마다 실제 파일을 다시 Read

문서 내용을 이 명령 파일에 옮겨 적지 않고, 실행할 때마다 아래를 전부 실제 파일로 다시 읽습니다.

**콘텐츠 철학 문서 (`docs/00`~`docs/07`, 번호 순서)**
1. `docs/00-AI-WRITING-CONSTITUTION.md`
2. `docs/01-BRAND-BIBLE.md`
3. `docs/02-INTERVIEW.md`
4. `docs/03-WRITING-GUIDE.md`
5. `docs/04-MEDICAL-COMPLIANCE.md`
6. `docs/05-SEO-AEO.md`
7. `docs/06-CONTENT-WORKFLOW.md`
8. `docs/07-EVIDENCE-BASED-COLUMN-GUIDE.md` — **이 명령의 핵심 지침**. 04와 함께 가장 비중 있게
   적용합니다.

문서가 비어 있거나 초안이면 그 사실을 그대로 보고하세요. 충돌 판단은 `CLAUDE.md`를 따릅니다
(**00 → 04 → 01 → 03 → 07 → 05**, 02는 근거 자료로만, 06은 SOP). 불명확하면 임의로 결정하지
말고 사용자에게 물어보세요.

**같은 주제와 관련된 기존 칼럼**
- `content/columns/`에서 같은 카테고리·태그·주제와 겹치는 기존 글을 찾아 읽으세요. 중복 주제인지,
  관련 글로 연결할 수 있는지 확인합니다.

**실제 프로젝트 구조**
- `lib/content/schemas.ts` — frontmatter 스키마. 이 명령도 여기 없는 필드를 추측해서 만들지
  않습니다(예: `references`/`citations` 같은 frontmatter 필드는 존재하지 않습니다 — 참고문헌은
  MDX 본문에 씁니다).
- `lib/jsonld.ts` — 실제 구현된 JSON-LD 빌더. `buildArticleJsonLd()`가 지원하는 필드만 사용하고,
  `citation`/`about`처럼 미구현 필드를 임의로 추가하지 않습니다(`docs/07` §11 참고).
- `lib/treatmentAnchors.ts`, `content/authors/*.mdx`, `components/content/mdx/mdxComponents.tsx` —
  `/칼럼쓰기`와 동일하게 확인합니다.

## 1단계 — 분석과 승인 요청 (여기서 반드시 멈춤)

1. **주제 분석**: 사용자가 준 주제를 임상적 질문 형태로 정리하고, `docs/07` 구조(임상적 질문 →
   짧은 답변 → 근거 → 한계 → 해석 → 프로토콜 → 요약 → 참고문헌)에 맞춰 어떻게 풀지 개요를 잡습니다.
2. **추가로 필요한 원장 인터뷰 질문**: `docs/02-INTERVIEW.md`를 읽었을 때 이 주제에 대한 원장의
   실제 판단 기준·프로토콜이 확인되지 않으면, 무엇을 확인해야 하는지 구체적으로 질문 목록을
   만들어 사용자에게 제시하세요(추측으로 채우지 않습니다).
3. **문헌 후보와 검증 결과**: `docs/07` §12의 절차대로 문헌 후보를 제안하고, 웹 검색/원문 접근이
   가능하면 PubMed·공식 학회 가이드라인 등 1차 출처를 직접 확인해 제목·저자·발행연도·저널명·DOI
   또는 PMID·연구 설계·대상자 수·주요 결과·임상적 한계를 정리하세요. 확인이 불가능한 문헌은 목록에
   넣지 말고, 사용자에게 원문/서지정보를 요청하세요. **이 단계에서 확인되지 않은 문헌을 만들어내지
   않습니다.**
4. **글의 구성안**: 예상 섹션 구성, 다룰 근거, 병원 프로토콜 섹션에 실제로 쓸 수 있는 내용이
   있는지(없으면 생략 예정임을 미리 밝힘)를 요약합니다.
5. **사용자 승인 요청**: 위 내용을 정리해서 보고하고 **명확한 승인을 받기 전까지 2단계로 넘어가지
   마세요.**

## 2단계 — 승인 후에만 실행

사용자가 문헌 목록과 구성안을 승인한 뒤에만 진행합니다.

1. **원고 작성**: `docs/07` 구조를 따르되, 조건부 권장 항목(인용 편수, 표, 질문형 제목, 개인차
   문구 등)을 억지로 채우지 않습니다 — 근거가 있는 것만 씁니다. 병원 언급은 "프로토콜" 섹션에서만.
2. **MDX 생성**: `content/columns/<slug>.mdx`. frontmatter는 `/칼럼쓰기`와 동일한 실제 스키마
   필드만 사용하고, `draft: true`로 생성합니다(발행은 `/칼럼발행`의 역할).
3. **썸네일 처리**: `/칼럼쓰기`와 동일한 절차 —
   ```bash
   node scripts/process-column-thumbnail.mjs "<원본 경로>" "<slug>"
   ```
   변환 도구가 없으면 원본 형식을 유지하고 그 사실을 정직하게 보고합니다. 새 패키지를 임의
   설치하지 않습니다.
4. **FAQ 및 메타데이터**: `frontmatter.faq`는 실제로 승인받은 문헌·본문에서 나온 질문일 때만
   채웁니다. 화면에 없는 FAQ를 만들지 않습니다.
5. **현재 지원되는 구조화 데이터 반영**: `lib/jsonld.ts`가 이미 만드는 Article(+MedicalWebPage,
   검토자가 있을 때)/BreadcrumbList/FAQPage(있을 때) 그대로 갑니다. `citation`/`about` 같은
   미구현 필드를 추가하지 않습니다.
6. **FAQ Knowledge Base 연동**: MDX가 완성되면(아래 7번 검증 전에) `docs/06-CONTENT-WORKFLOW.md` §16을 실제 파일로 다시 읽고 그대로 따르세요. `/칼럼쓰기`와 동일한 규칙입니다 — 이 명령 파일에 규칙을 복사해 적지 않습니다. `content/faq/*.mdx` 전체를 다시 읽고, 같은 search intent의 기존 FAQ가 있으면 새로 만들지 않고 갱신·연결하며, 없고 독립 답변 가치가 있을 때만 최대 3개까지 `draft` 상태로 새 FAQ를 만듭니다. 후보가 없으면 0개로 끝내는 것이 정상입니다.

   학술칼럼 특유의 주의사항(§16-6과 동일): FAQ에서 연구 결과를 직접 언급할 때는 이미 이번 칼럼에서 검증한 문헌 metadata를 재사용하세요. FAQ를 쓰며 새 논문을 추가로 찾는 것을 기본 동작으로 하지 않습니다 — 모든 FAQ에 논문을 붙이는 것도 목표가 아닙니다. 실제로 근거가 필요한 주장에만 적용하세요.

7. **전체 검증 및 build**:
   ```bash
   npm run validate:content
   npm run validate:seo
   npm run typecheck
   npm run lint
   npm run build
   ```
   하나라도 실패하면 원인을 고치고 재실행하세요. 실패 상태로 "완료"라고 보고하지 않습니다.

## 절대 하지 말 것

- 1단계 승인 없이 `content/columns/`에 파일 생성
- 확인되지 않은 논문·DOI·PMID·저자·수치·프로토콜 생성
- 존재하지 않는 frontmatter 필드나 JSON-LD 필드 추가
- `git add`/`commit`/`push` — 발행은 `/칼럼발행`으로 별도 수행
- schema 변경, 디자인/CSS 리팩토링, 기존 코드 정리, 칼럼과 무관한 파일 수정, 패키지 임의 설치
- 다른 병원·다른 술식 비판, 학술 정보 밖 병원 홍보 문장 삽입

## 최종 보고 (2단계 완료 후)

- 최종 frontmatter 전체
- 사용된 문헌 목록과 각 문헌의 근거 수준
- **FAQ Knowledge Base 결과** (`docs/06` §16-9 형식 — 신규 FAQ / 기존 FAQ 업데이트 / semantic duplicate로 미생성 / FAQ 추가 필요 없음 중 실제 해당하는 것만. 개수를 목표로 보고하지 않습니다)
- 검증 명령 5개의 결과
- localhost 확인 URL
- `docs/06` §15에 준하는 체크리스트(00~07 확인 여부 포함)

# /칼럼삭제

칼럼을 삭제합니다. **이 명령은 두 단계로 나뉩니다: (1) 영향 분석 및 보고, (2) 사용자의 명확한 확인 후 실제 삭제.**
1단계가 끝나면 반드시 멈추고 사용자의 응답을 기다리세요. 같은 턴에서 곧바로 삭제까지 진행하지 마세요.

사용자 입력(`$ARGUMENTS`): 삭제할 칼럼의 slug.

## 1단계 — 영향 분석 (읽기 전용, 아무것도 삭제하지 않음)

1. `content/columns/<slug>.mdx`가 실제로 존재하는지 확인하세요. 없으면 그렇게 보고하고 종료하세요.
2. 해당 파일의 frontmatter를 읽어 `thumbnail` 경로, `featured`, `category`, `tags`, `relatedTreatmentSlugs`를 확인하세요.
3. **공유 이미지 여부 확인**: `grep -rl "<thumbnail 경로>" content/columns/`로 이 썸네일을 다른 글도 쓰고 있는지 확인하세요. 다른 글과 공유 중이면 절대 이미지를 삭제 대상에 넣지 마세요.
4. **관련 글 영향**: 다른 published 칼럼들이 같은 `category`이거나 겹치는 `tags`를 가지고 있어 `lib/related.ts`의 관련 글 추천에 이 글이 나타날 가능성이 있는지 확인하세요(삭제되면 그 글들의 "관련 글" 결과가 자연스럽게 줄어들 뿐이며 별도 조치는 필요 없습니다 — 다만 사용자에게 언급은 하세요).
5. **홈/목록 노출 영향**: `featured: true`인 경우 홈 컬럼 티저와 `/column` 추천 영역에서 사라진다는 점을 명시하세요. 남은 published 글이 없다면 홈 티저 섹션 자체가 보이지 않게 된다는 점도 확인해 언급하세요(`components/sections/home/ColumnTeaserSection.tsx`의 fallback 정책).
6. **sitemap/RSS 영향**: 삭제되면 `/column/<slug>`가 다음 빌드부터 sitemap.xml/rss.xml에서 자동으로 빠집니다(내용이 실제 파일 존재 여부를 기준으로 생성되므로 별도 수정 불필요) — 단, 이미 검색엔진에 색인되어 있었다면 삭제 후 404가 된다는 점은 사용자에게 알려주세요.
7. **삭제 대상 파일 목록을 정확히 보고**하세요: `content/columns/<slug>.mdx`, 그리고 (2단계에서 확인한) 전용 썸네일 파일이 있다면 그 경로.

**여기서 멈추세요.** 위 내용을 요약해서 사용자에게 보고하고, 명확한 삭제 확인을 받기 전에는 어떤 파일도 지우지 마세요.

## 2단계 — 사용자가 명확히 확인한 뒤에만 실행

1. `content/columns/<slug>.mdx` 삭제.
2. 1단계에서 "다른 글과 공유되지 않음"이 확인된 전용 썸네일만 삭제. 조금이라도 공유 여부가 불확실하면 삭제하지 말고 그대로 두세요(이미지 삭제는 되돌리기 어렵습니다 — 확신 없으면 보수적으로 남겨두는 쪽을 선택).
3. 검증을 실행하세요:
   ```bash
   npm run validate:content
   npm run validate:seo
   npm run typecheck
   npm run lint
   npm run build
   ```

## 절대 하지 말 것

- 명확한 사용자 확인 없이 삭제 진행
- 공유 여부가 불확실한 이미지 삭제
- `git add`/`commit`/`push` — 이 명령의 범위가 아닙니다. 실제 반영은 `/칼럼발행`으로 별도 수행합니다(단, 삭제의 경우 `/칼럼발행`도 "삭제를 커밋"하는 흐름에 맞게 대상 파일을 `git add`해야 함을 사용자에게 안내하세요).

## 최종 보고 (2단계 완료 후)

- 삭제된 파일 목록
- 검증 결과
- 이번 삭제가 아직 커밋되지 않았고, `/칼럼발행`으로 별도 반영해야 한다는 점

# /칼럼업데이트

이미 존재하는 칼럼을 수정합니다. 새 글 생성이 아니라 **기존 파일 편집**입니다.

사용자 입력(`$ARGUMENTS`): 수정할 기존 칼럼의 slug, 그리고 수정할 원고 또는 구체적인 변경 요청. 선택적으로 새 썸네일.

## 1. 먼저 읽기 (수정 전 반드시)

- `docs/00-AI-WRITING-CONSTITUTION.md`부터 `docs/06-CONTENT-WORKFLOW.md`까지 번호 순서대로
  이번 실행에서 다시 Read하세요(문서 내용을 이 명령 파일에 옮겨 적지 않고, 실행마다 실제 파일을
  다시 읽습니다). 비어 있거나 초안 상태면 그 사실을 그대로 보고하고, 있는 것처럼 요약하지 마세요.
  문서 역할과 충돌 판단 기준(00 → 04 → 01 → 03 → 05, 02는 근거 자료로만, 06은 SOP)은
  `CLAUDE.md`를 따르세요.
- `content/columns/<slug>.mdx` 전체를 읽으세요. 존재하지 않으면 여기서 멈추고 보고하세요.
- 현재 `thumbnail`이 가리키는 파일을 확인하세요.
- `lib/content/schemas.ts`를 다시 확인해 스키마가 바뀌지 않았는지 확인하세요.

## 2. 수정 범위를 먼저 보고

실제로 파일을 바꾸기 전에, 무엇을 어떻게 바꿀 계획인지 요약해서 사용자에게 보고하세요(어떤 문단/필드가 바뀌는지). 요청받은 변경 범위를 벗어나는 내용(문체 전면 수정, 관계없는 섹션 재작성 등)을 임의로 추가하지 마세요.

## 3. 규칙

- **slug는 명시적 요청이 없으면 절대 바꾸지 마세요.** slug를 바꾸면 파일명도 함께 바꿔야 하고, 기존에 그 URL을 참조하는 sitemap/RSS/관련 글/외부 링크가 깨집니다 — 정말 필요한 경우에만, 사용자가 명확히 요청했을 때만 수행하고 영향 범위를 먼저 보고하세요.
- **`publishedAt`은 그대로 유지하세요.** 최초 발행일입니다.
- **`updatedAt`을 실제 수정일(오늘 날짜, `YYYY-MM-DD`)로 설정하세요.** `updatedAt`은 `publishedAt`보다 이전일 수 없습니다(스키마 제약).
- 새 썸네일이 제공된 경우, `/칼럼쓰기`와 동일한 방식으로 처리하세요:
  ```bash
  node scripts/process-column-thumbnail.mjs "<원본 경로>" "<slug>"
  ```
  기존 썸네일 파일을 교체할 때는 다른 글이 같은 이미지를 공유해서 쓰고 있지 않은지 먼저 확인하세요(예: 여러 글이 `/images/consult.png` 같은 공용 이미지를 재사용 중일 수 있습니다 — `grep -rl "이미지경로" content/columns/`로 확인). 이 글 전용 이미지가 아니면 함부로 덮어쓰지 마세요.
- 본문을 수정할 때도 H1을 넣지 않고, 존재하지 않는 MDX 컴포넌트(`Testimonial`, `FAQBox` 등)를 사용하지 마세요 — `/칼럼쓰기`의 "본문 작성 규칙"과 동일하게 적용됩니다.
- `frontmatter.faq`를 수정한다면, 이 값이 상세 페이지의 FAQPage JSON-LD와 화면 표시의 단일 데이터 소스라는 점을 유지하세요 — 별도로 하드코딩된 FAQ 콘텐츠를 만들지 마세요.
- 내부 링크(`relatedTreatmentSlugs`, 본문 링크)가 여전히 실제 존재하는 경로를 가리키는지 확인하세요.
- 환자 개인정보, 임의 사실 생성 금지 — `/칼럼쓰기`와 동일합니다.
- **의료광고 금지 표현 검사는 `docs/04-MEDICAL-COMPLIANCE.md`의 최신 내용을 직접 읽고 그 기준 그대로 적용하세요.** 이 명령 파일 안에 별도로 요약된 금지어 목록을 두지 않습니다 — 1번에서 이미 다시 읽은 04를 그대로 기준으로 씁니다.

## 4. 검증 (반드시 직접 실행)

```bash
npm run validate:content
npm run validate:seo
npm run typecheck
npm run lint
npm run build
```

## 5. 절대 하지 말 것

- `git add`/`commit`/`push` — 이 명령의 범위가 아닙니다. 반영은 `/칼럼발행`으로 별도 수행합니다.
- slug 임의 변경
- `publishedAt` 변경
- 요청 범위를 벗어난 문체/구조 전면 수정
- **schema 변경** (`lib/content/schemas.ts` 등)
- **디자인/CSS 리팩토링**
- **기존 코드 정리(리팩토링)**
- **칼럼과 무관한 파일 수정**
- **새 패키지 임의 설치**
